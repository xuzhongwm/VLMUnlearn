# VLM cross-modal unlearning — Stage 1 (reproduce the asymmetry)

Does unlearning facts through **text-only** questions transfer to **image+text** questions about
the same facts? Stage 1 reproduces the asymmetry cleanly on MLLMU-Bench (forget_10). It uses:
- fact-paired, paraphrased MC items;
- our own vanilla model, trained on both forms;
- GA / GA_Diff / NPO with LoRA;
- comparison at matched in-modality forgetting.

The design and every decision are in [PLAN.md](PLAN.md). Results go in `RESULTS.md` once the runs are done.

## How to run (Google Colab, A100 40 GB preferred)

Open [colab/run.ipynb](colab/run.ipynb) and set `REPO_URL` and `MODEL` in cell 1. Then run the
cells in this order:

| # | cell | what it does | A100 runtime (Phase A: `qwen2vl`) | A100 runtime (Phase B: `llava`) |
|---|---|---|---|---|
| 1 | Setup (3 cells) | mount Drive, clone/pull repo, pip install | ~2 min | ~2 min |
| 2 | Data | download MLLMU-Bench + MMBench to Drive; build paired items; 21 data checks | ~10 min (once, shared by both models) | — |
| 3 | Smoke test | every job below with `--debug` (~20 samples) | ~10 min | ~15 min (first 14 GB weight download) |
| 4 | Pretrained baseline | base model, no FT, full eval (priors) | ~3 min | ~6 min |
| 5 | Vanilla FT + gate | LoRA FT on both forms, 3 epochs; full eval; gate ≥ 80% in both modalities | ~0.8 h | ~2.5 h |
| 6 | Unlearning grid | 18 runs (3 methods × 2 modalities × 3 lr), seed 0 | ~2.6 h | ~7 h |
| 7 | Selection + seeds | matched checkpoint per cell, full eval, seed-1 reruns | ~0.8 h | ~2.6 h |
| 8 | Aggregate + sanity | transfer tables, figure, verdict, sanity report | 1 min | 1 min |
| 9 | (optional) push results | commit `results/` from Colab | — | — |
| | **total** | | **≈ 4.5 h** | **≈ 12.5 h** |

**Order and stopping points:**
- Run Phase A (`MODEL = "qwen2vl"`, cells 1–8) first. Then set `MODEL = "llava"` and run cells 1, 3–8. Cell 2 is only needed once.
- If cell 5 prints `GATE FAILED`, stop: unlearning is blocked by design (D2). Report the gate numbers instead.

**About the estimates:**
- They come from the throughput assumptions in PLAN.md §7. The smoke-test logs print the measured `s/step`, which tells you whether they hold.
- L4 (24 GB) works too and is about 2.5–3× slower. If LLaVA training runs out of memory there, add `--set train.batch_size=2` to cells 6–7.

**After a disconnect:** re-run the setup cells, then the cell you were on.
- Training resumes from the last checkpoint (every ½ epoch in unlearning, every 500 steps in vanilla FT).
- Evaluation skips items that are already scored.
- Finished runs are skipped.
- Kill-and-resume was tested locally: the result is identical to an uninterrupted run (same checkpoint metrics, bit-identical adapter).

## Outputs (`/content/drive/MyDrive/vlm_unlearn/`)

```
data/raw/                     HF downloads (~1.4 GB)
data/processed/               items_*.jsonl, train/unlearn sets, images, build_report.json, sanity_data.json
models/<model>_vanilla/       vanilla LoRA adapter (merged into the public base at load time)
runs/<model>/pretrained/      full eval of the base model
runs/<model>/vanilla/         FT log, checkpoint evals, gate.json, full_eval/
runs/<model>/unlearn/<run>/   config.json, log.txt, checkpoints.jsonl (every grid point), best_adapter/, evals/
results/run_log.csv           every job start / done / failed / interrupted (nothing is dropped silently)
results/<model>/              grid.csv, selection.json, selected_runs.json, transfer_table.csv,
                              asymmetry.csv, verdict.json, sanity.json, transfer_<model>.png, generated_configs/
results/transfer_table.csv    all models combined (also mirrored to this repo's results/)
debug/                        same layout for --debug runs
```

Drive space needed is about 5 GB. Base weights are re-downloaded to local disk each session.

## Repo layout

```
vlmu/data/     raw download, field extraction, "this person" -> name rewrite, paired-item builder, data checks
vlmu/models.py Qwen2-VL / LLaVA adapters: prompts, answer-only labels, A-D letter scoring, LoRA targets
vlmu/train.py  resumable LoRA loop; GA, GA_Diff, NPO, NLL
vlmu/evaluate.py, vlmu/metrics.py   MC scoring (resumable), normalised drop, profile-cluster bootstrap
vlmu/runs.py   job orchestration: vanilla+gate, grid runs, selection, seed reruns
vlmu/report.py transfer table, asymmetry, GO/NO-GO rule, figure
configs/       data.yaml, models/*.yaml, <model>/{vanilla,grid}.yaml, <model>/runs/*.yaml (one per run)
scripts/       job entry points (each supports --debug, --root, --set key=value)
colab/run.ipynb
```

Every run is fully defined by its YAML. Grid runs live in `configs/<model>/runs/`, generated by
`scripts/make_run_configs.py`. Seed reruns are written to `results/<model>/generated_configs/`.
The resolved config is also saved in each run dir.

## Local testing (no GPU)

The whole pipeline runs on CPU with tiny random-weight models:

```bash
python scripts/smoke_test.py --model qwen2vl --root /tmp/vlmu \
  --set model.id=hf-internal-testing/tiny-random-Qwen2VLForConditionalGeneration
python scripts/smoke_test.py --model llava --root /tmp/vlmu \
  --set model.id=trl-internal-testing/tiny-LlavaForConditionalGeneration
```

## Known risks

- **Pinned versions:** `transformers==4.51.3` and `peft==0.15.2`; torch comes from the Colab image. If a future Colab torch breaks this, pin torch too (tested locally with torch 2.6.0).
- **Vanilla recipe:** lr 2e-4, 3 epochs, batch size 8 is our choice. MLLMU's own recipe reached only ~52% on official MC. If the gate fails, the fix (e.g. more epochs) is a change to the vanilla config and gets logged. It is not tuned per condition.
